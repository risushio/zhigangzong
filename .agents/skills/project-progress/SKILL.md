# Project Progress

## 范围与触发

项目根目录是包含本 Skill、`pom.xml`、`package.json` 和应用 `.git/` 的 `zhigangzong/`，不是外层工作区。始终先读取根目录 `AGENTS.md` 和现有记录，使用项目实际命令；以后项目结构变化时重新检查，不盲用旧命令。

- 日常开发：完成一个独立功能、改进、Bug 修复或文档变更时执行 Workflow A，无需用户另行提醒。
- 发布：只有用户明确输入如 `发布 v1.1.0`、`release v1.1.0` 才执行 Workflow B。显式 `$project-progress` 但未要求发布时，不创建 Release。
- 只准备发布说明、检查发布条件或举例版本号时，不创建 tag、推送或发布。

## 记录约束

`complete.md` 只保存当前尚未发布版本的已完成且已验证的工作。计划/TODO 保留于 `docs/NEXT-STEPS.md` 等计划文件；不搬入完成记录。`CHANGELOG.md` 保存永久版本历史。

不要因代码已修改、提交已创建或工具调用成功就判定功能完成。不记录未通过、未执行或关键检查被跳过的工作；不得绕过失败测试。记录与发布说明不得包含密钥、Token、密码、`.env` 内容、业务个人数据或内部推理。不要读取私密配置来编写日志。

## Workflow A — 完成开发任务

1. 实现一个可独立验收的变化，检查最终代码与任务要求。
2. 按影响选择验证，并核实退出码及结果：
   - 前端：`npm run check` 和 `npm test`，有交互变化时验证对应页面流程。
   - 后端：`.\scripts\maven.ps1 verify`；涉及数据库、权限或业务闭环时追加 `.\scripts\test-mysql.ps1`，必要时运行 smoke 与对应流程。
   - 纯文档/Skill：检查 Markdown/YAML、路径/链接及规则一致性；Skill 使用可用的内置 `skill-creator/scripts/quick_validate.py` 验证。不要把文档校验描述成业务测试已通过。
   - 新增或调整构建/运行配置时，验证实际构建与受影响的启动入口。
3. 验证失败则继续修复并重新验证，不更新完成记录。缺少工具/数据库或无法验证时报告具体阻塞，也不登记完成。此前记录的完成项被后续修改破坏时，移除或收窄受影响内容，直到修复通过。
4. 验证成功后再次读取 `complete.md`，以最终行为和范围判断是否已有条目。相同功能更新原条目；小幅修复并入原项，独立问题记入 Bug Fixes。不要仅按文字是否完全相同去重。
5. 分类写入 `## Unreleased` 的 Features、Improvements、Bug Fixes 或 Documentation。一个独立变化只选主要分类；使用 `- [x]`，面向用户说明项目行为，必要时补充范围与一条简短验证依据。

示例（只有对应验证实际通过才使用）：

```markdown
- [x] 支持按城市筛选已审核岗位
  - 学生可组合城市和关键词查询。
  - 验证：前端语法检查、契约测试及筛选页面验收通过。
```

不要记录“我修改了某 Controller”或大量文件级修改。不根据旧 README、commit 标题或计划猜测完成项。保留文件已有有效内容；创建时使用四分类空结构。

## Workflow B — 发布版本

### 1. 发布前检查与验证

1. 确认用户明确授权本版本发布，规范版本 `X.Y.Z` 和 tag `vX.Y.Z`（需要预发布版本时遵循用户指定后缀）；日期采用 Asia/Shanghai。未指定必要版本时先准备可确定的内容再澄清，不猜测版本。
2. 在应用根目录检查 `git status --short`、分支、HEAD、远程、已有 tags、GitHub Releases 及权限。不要使用外层仓库；不要向未知或不匹配的远程发布。保留用户已有修改；只提交明确属于本次发布的文件，禁止 `git add .` 搭带无关内容。发布候选必须有确定的提交与完整内容；无法判定未提交改动是否属于版本时，停止外部发布并说明具体冲突。
3. 检查可用 GitHub 发布能力：优先支持创建/查询 Release 的连接器；否则检查 `gh --version`、`gh auth status` 和目标仓库权限。没有可用发布接口或认证时，可准备本地说明，但在创建 tag/推送之前停止。不要输出 Token 或自动安装/配置凭据。当前检查结果只是快照，未来每次发布重新检查。
4. 完整运行 `npm run check`、`npm test`、`.\scripts\test-mysql.ps1`（调用 Maven verify 并构建，开启 MySQL 测试）。核实测试数量、关键测试是否跳过及构建产物；不能把条件跳过的集成测试视为通过。后端启动后执行 `.\scripts\smoke.ps1`，并按版本变化验证对应用户流程。
5. 验证候选构建能够实际运行：优先使用隔离本地配置/端口启动刚构建的产物并验证健康、数据库和受影响流程。已有服务的 smoke 不能证明新产物可运行；不得贸然停止他人服务。数据库集成测试遵循既有事务回滚机制，不清空业务数据。
6. 本项目 `scripts/start.ps1` 当前硬编码 `1.0.0` JAR 路径。升级版本时检查 `pom.xml`、`package.json`、运行入口及说明的一致性，必要时修正启动脚本，再对最终候选重新验证。禁止使用 `-DskipTests` 等手段掩盖失败。关键验证失败或依赖不可用时停止发布，保留记录并报告原因。

### 2. 整理版本说明

1. 保存本次 `complete.md` 的发布快照与候选提交。读取上一条已发布 GitHub Release 的 tag/目标提交，对照该提交至候选的 diff、log 和已有说明；没有上一条 Release 时明确按首次发布处理，不把任意最近 tag 当成已发布 Release。
2. 对照变化核查条目：过滤已在旧版本发布的内容，合并重复和过细项目。Git diff/log 仅用于核对，不能替代验证证据；遗漏的独立功能必须验证后按 Workflow A 补录。不能验证的内容阻塞候选或从发布范围中排除，不能冒充完成。
3. 为读者撰写简洁 Release Notes：标题 `# vX.Y.Z`、一段版本重点，以及非空的 `✨ Features`、`🚀 Improvements`、`🐛 Bug Fixes`、`📚 Documentation`。保留影响用户的兼容性、迁移要求和真实限制，省略执行流水账与详细测试日志。没有有效完成项时，不捏造变化；说明空版本原因，缺乏用户明确意图时停止。
4. 将完整说明保存到 `docs/releases/X.Y.Z.md`（如已有同版本文件，先核实而非覆盖），把永久摘要写入 `CHANGELOG.md` 顶部现有版本之前，格式为 `## [X.Y.Z] - YYYY-MM-DD` 和四分类中的非空小节，版本间用 `---` 分隔。不覆盖旧版本、不重排历史。相同版本重试时复用/校正本次条目，不重复插入版本。
5. 对最终候选做必要复验，并明确暂存本次相关文件，创建发布提交，确认提交内容与验证对象一致。此时 `complete.md` 保留本次条目；归档清空必须在 GitHub 发布确认成功之后。

### 3. tag、推送与 GitHub Release

1. 读取本地与远程是否已有目标 tag/Release。新 tag 使用 annotated tag 指向经过验证的发布提交。已存在则核对 SHA 和状态；仅在同一候选匹配时复用。冲突时停止，不移动、删除或覆盖旧 tag/Release。
2. 正常推送必要的发布提交及该 tag，显式指定目标分支和单个 tag；不要 `--force`、`--mirror`、批量推送无关 tags 或删除远程分支。遇到保护规则/权限/拒绝推送时停止并保留记录，按仓库既有 PR 流程处理，不绕过保护。
3. 使用支持的连接器创建对应版本的正式 GitHub Release。使用 CLI 时将说明存为 UTF-8 文件，以 `gh release create` 的 `--notes-file`、`--verify-tag` 和显式 `--repo` 参数发布，避免 shell 拼接多行文本；不要用 GitHub 自动生成 commit 清单替代整理后的说明。预发布版本按用户指定使用 prerelease 标志。只在任务包含产物时附加检查过的构建产物，不上传本地配置、数据库或用户文件。
4. 查询 Release 确认 URL、tag、目标 SHA、说明及非 draft 状态正确。超时或响应不明确时先查询远程，不能盲目重复创建，也不能假定失败后删除远程资源。已有同版本 Release 时仅核对其与本次候选的一致性，不能静默覆盖他人发布。

### 4. 成功后归档与失败恢复

- 只有确认对应 GitHub Release 已发布且匹配本次候选后，才清除本次发布快照中的 Unreleased 条目，保留 `# Completed Work`、`## Unreleased` 和四分类结构。无并发新增时恢复为空结构；若开发期间新增了下一个版本的完成项，只移除已发布条目，保留新项。
- 历史已存于 `CHANGELOG.md`、`docs/releases/X.Y.Z.md`、GitHub Release 与 Git history。清空后创建单独的归档提交并正常推送，不移动版本 tag；tag 继续指向已验证的发布提交。
- 创建 Release 失败、认证失败、推送失败或状态不确定时，不清空 `complete.md`。保留已准备的说明，报告失败阶段、已存在的提交/tag/Release 与重试入口，不通过危险 Git 操作回滚。
- Release 成功但归档提交/推送失败时，报告“已发布，归档未同步”，保留本地归档更改。下一次先查询已发布版本，再完成归档；不要重复发布或重复添加 CHANGELOG。完整恢复前不要开始下一版本发布。
- 最终报告版本、验证摘要、发布提交/tag、Release URL 与归档是否同步；不得把未完成步骤报告为成功。
