## 1. 产品定位

以学校认可的岗位为基础，连接学生匹配、实习审批、过程指导、风险处理和成果评价。

建议从一个学校或学院的毕业实习场景起步，以学校为主要管理方，服务学生、校内指导教师、企业招聘人员及企业导师。

核心业务流程：

学生完善档案 → 企业与岗位审核 → 岗位推荐与双向选择 → 学校批准及入岗准备 → 实习过程指导 → 异常处理 → 多方评价 → 结项归档。

学生自主联系的单位也应支持申报、审核和后续管理，不要求所有学生都通过平台找岗位。

### 关键业务要求

- 招聘录用与学校实习批准分别记录；获得录用不自动代表满足毕业实习要求。
- 岗位应明确标注审核状态和适用专业，不把平台发布等同于学校认可。
- 实习变更保留历史记录，不能直接覆盖原单位、岗位和审批结果。
- 异常处理应包含责任人、跟进记录和处理结果，不只显示预警数量。
- 教师及企业人员只访问履行职责所需的数据。
- 报表指标应明确统计口径，例如落实率的统计对象、时间及确认条件。
- 签到按实际需求启用，预留人工确认、补签和申诉方式。

## 5. 智能匹配的具体范围

| 能力 | 建议行为 |
| --- | --- |
| 硬性条件检查 | 检查实习时长、到岗日期和每周到岗天数；不满足时明确提示冲突 |
| 专业与培养目标匹配 | 判断岗位内容是否符合该专业的毕业实习要求，并允许教师确认 |
| 技能与经历匹配 | 展示已有技能、项目经历与岗位要求的对应关系 |
| 意愿匹配 | 考虑城市、报酬、到岗时间和出勤天数等学生偏好 |
| 推荐解释 | 展示适配项、缺失项及信息不足，例如“时间和专业符合要求，但缺少 SQL 项目经验” |
| 人工调整与反馈 | 学生可以忽略推荐，教师可以调整；记录不感兴趣或不适合的原因 |

匹配分数表示适配程度，不应包装成录用概率。推荐辅助选择，不能自动决定录用、学校批准或实习成绩。

第一版可采用可解释的条件筛选与规则评分；是否引入复杂模型，依据试点数据和真实效果决定。新学生或新岗位缺少数据时，仍应支持正常搜索和人工选择。

涉及个人信息自动化决策时，应关注透明、公平、解释及拒绝机制；依法开展必要的个人信息保护影响评估。具体适用要求需结合实际处理方式确定。

| 移动端或微信小程序 | 方便提交材料、处理待办；先验证使用场景再确定形式 |
| 电子签约 | 接入适用的电子签约服务；第一版先支持文件上传，文件上传不等同于电子签约 |
| 实习转就业跟踪 | 记录转正、就业意愿和毕业去向反馈，与实习成绩分开管理 |
| 多学校管理 | 学校数据隔离、各校独立配置，支持后续推广 |

## 7. 建议暂缓的功能

| 功能 | 暂缓原因与替代方向 |
| --- | --- |
| 持续 GPS 追踪、人脸签到 | 先验证必要性；优先按需签到和人工确认。行踪轨迹及生物识别涉及敏感个人信息 |
| 自动心理风险标签、自动认定造假、自动评分 | 先提供可核查的异常线索，保留人工复核与申诉 |
| AI 代写周报 | 可辅助整理学生提供的事实，不生成虚构实习经历 |
| 全国岗位爬取 | 岗位来源、授权、更新和质量维护成本较高，先建设学校合作岗位库 |
| 直播招聘、社交社区 | 与早期核心流程关系较弱，先验证一个学院能否完成全过程管理 |

## 8. 建议优先打磨的差异化方向

1. **符合专业培养要求的岗位匹配**：推荐依据不仅包含求职偏好，也包含专业要求、实习时间和学校认可情况。
2. **学生问题的及时跟进**：从求助或异常发现，到责任人接收、跟进、处理结果和复核，形成完整记录。
3. **教师审核与归档减负**：减少重复填报和重复催交，让教师快速找到缺失材料、待批阅内容及需联系的学生。

这些方向有公开需求依据，但是否能形成竞争优势，仍需通过实际访谈和试点验证。

## 9. 后续推进建议

### 第一步：访谈并确认需求

建议访谈学生、校内指导教师、学院管理人员及企业人员，重点确认：

- 当前使用哪些系统、表格或沟通工具，哪些信息需要重复填写。
- 是否已有实习平台，哪些问题仍未解决，学校愿意补充功能还是替换系统。
- 岗位由谁提供、谁审核，学生自主实习的比例及审核方式。
- 不同专业的材料、签到、实习时长和评价要求。
- 异常由谁处理，怎样确认已经解决。
- 企业愿意参与哪些环节，如何减少企业导师的操作负担。
- 实际采购决策方、预算来源、部署要求和校园系统接入条件。

### 第二步：确定单学院试点范围

选择一个学院或专业、一批学生和若干合作企业，先跑通匹配、审批、过程记录、异常处理、评价和归档。

在开发前明确试点用户、岗位来源、制度模板、角色职责和验收标准。暂不直接铺设全国招聘或多学校平台。

### 第三步：用指标验证效果

建议记录并比较试点前后的：

- 学生找到并获批实习岗位所需时间。
- 岗位推荐后的有效申请与录用情况。
- 教师批阅、催交和统计耗时。
- 材料按时提交率及结项完成率。
- 异常首次响应时间、处理时间及复核情况。
- 学生、教师和企业的使用反馈。

先确定统计口径和基线，不预先承诺提升幅度。

### 第四步：确认需求后再确定技术方案

根据试点规模、学校系统接口、移动端需求、数据保护和部署条件，继续确认开发顺序。当前本地版本采用 Java 17、Spring Boot、MyBatis、Maven、MySQL 与原生 JavaScript，已实现流程见上文；后续扩展方案仍需业务验证。

优先形成可使用的核心流程，再根据实际反馈引入 AI 增强、电子签约、系统对接和多学校支持。
